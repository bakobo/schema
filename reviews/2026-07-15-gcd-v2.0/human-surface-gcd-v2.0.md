# Human-Surface Review: bakobo/schema

**Date / Effort / Commit:** 2026-07-15 / medium / 735f60b (main)
**Persona:** HSX (human-surface) · run label: gcd-v2.0 · mode: unattended

---

## Surfaces inventoried

This repo has no interactive UI or application frontend. The user-facing surfaces are:

1. **CLI tool (`schematools`)** — `check`, `saidify`, `saidify-sad`, `registry`, `publish`, `build-docs` subcommands. Output printed to stdout and stderr. Primary audience: schema authors and CI. Errors surface via `Problem.__str__` and raw Python exceptions.
2. **`index.html` landing page** (generated by `publish.build_site`) — the public-facing HTML registry at schema.bakobo.com. Machine-generated from `_render_index()` in `tools/py/src/schematools/publish.py`.
3. **Per-schema `index.md` documentation files** — narratives served as browsable pages through Zensical. These are what end users (credential verifiers, issuers, ecosystem participants) read to understand each credential type. Files: `gcd/index.md`, `ai-coder/index.md`, `ai-user-coca/index.md`, `attestation/index.md`, `award/index.md`, `bindkey/index.md`, `citation/index.md`, `faa/index.md`, `face-to-face/index.md`, `org-vet/index.md`, `proof-of-control/index.md`.
4. **Schema `description` and `title` fields in `*.schema.json`** — surfaced in the HTML registry table and in Zensical doc pages via `_schema_description()`.
5. **`README.md`** — the GitHub landing page for the repo.

Error-tracing method: followed each user-reachable failure path from `cli.py` main dispatch through `repo.find_repo_root()`, `checks.Problem.__str__`, and `publish.build_site()` to the text a person actually reads.

---

## Executive summary

The bakobo/schema human surface is largely functional and technically appropriate for its audience of credential authors and ecosystem participants. Its most significant cost-shifting is the absence of proper English in the CLI: `"3 problem(s) across 12 schema(s)"` forces the reader to mentally parse mechanical machine-style output rather than natural English, and raw Python tracebacks surface when the repo root cannot be found. The most concentrated prose defects are in `proof-of-control/index.md`, which has five distinct grammar/spelling errors in two paragraphs — these appear in every verifier's first read of that schema. The most urgent fix is the CLI error-surface: adding a clean handler for `FileNotFoundError` from `find_repo_root()` so the user gets an actionable sentence instead of a traceback.

## Five-axis assessment

### Axis 1 — Error quality

**Verdict: MEDIUM concern.** The `Problem.__str__` format (`[check] where: message`) is a developer-readable log line, not a user-facing sentence. The messages themselves are reasonably descriptive (they name what failed and include offending values), but they carry no stable symbolic code (e.g., no `SCHEMA_SAID_MISMATCH`), no permanent-vs-transient signal, and they are not complete sentences.

Worst offender: `find_repo_root()` in `repo.py:26` raises `FileNotFoundError(f"no {REGISTRY_NAME} found at or above {here}")`. The CLI's `main()` function has no handler for this, so the user running `schematools check` outside a schema repo gets a full Python traceback. This is a dead-end error that dumps internal detail without telling the user what to do.

Rewritten: `"I couldn't find a schema repo here. I walked up from {here} looking for registry.json and found nothing. Run this command from inside a schema repo, or pass --root to point me at one."`

The `check` subcommand's error stream (`[said] gcd/gcd.schema.json: $id 'X' != recomputed 'Y'`) is acceptable for a developer-facing linter, but the standard requires a stable symbolic code at a minimum. Without one, CI scripts must string-match `[said]` rather than branch on a documented constant.

### Axis 2 — Voice and tone

**Verdict: MEDIUM concern.** The primary issues are:

1. **`(s)` suffix anti-pattern** throughout CLI output: `"problem(s)"`, `"schema(s)"`. The brand voice standard requires complete, natural-language sentences. This is a machine shorthand, not English. It forces the reader to parse rather than read. Affect: every run of `schematools check`, `publish`, `build-docs`.

2. **Multiple grammar and spelling errors in `proof-of-control/index.md`**:
   - Line 20: "The parties **follows**" — subject-verb agreement error; should be "follow".
   - Line 24: "This is **a** random number" — missing article.
   - Line 36: "issuee's **idetifier**" — "identifier" misspelled.
   - Line 38: "The issuee **should** digitally sign" — missing modal verb; current phrasing ("digitally sign") is a sentence fragment.
   - Line 47: "**crypographic** identifiers" — "cryptographic" misspelled.

3. **Other scattered typos in deployed doc surfaces**:
   - `gcd/index.md:7`: "**signifcantly** more secure"
   - `faa/index.md:31`: "because the **artfact** has no revocation semantics"
   - `ai-coder/index.md:17` and `award/index.md:19`: "employee**=**of-the-month" (= instead of -)
   - `gcd/gcd.schema.json:5`: "**first-classes** duties" — should be "first-class"
   - `attestation/index.md:5`: "the data**(cryptographic**..." — missing space before parenthesis; "**json** data" should be "JSON data"

4. **GCD schema description voice** (`gcd/gcd.schema.json:5`): "Define the authorizations..." — starts with a bare infinitive (imperative fragment) rather than a complete sentence. Better: "This credential defines the authorizations, duties, and constraints of a delegate who receives delegated authority."

### Axis 3 — UX and affordances

**Verdict: LOW concern** for this repo's surfaces. The CLI is well-structured: subcommands are logically named, `--root` auto-detection is explained in the help text, and failure output goes to stderr while the verdict goes to stdout (correct stream separation). The `check` command's `FAIL: N problem(s)` summary gives a clear pass/fail signal.

The `index.html` landing page clearly labels columns ("Schema", "Asserts", "Version", "OOBI (SAID)") and links both the schema path and the OOBI for each entry. The note "A richer browsable site is in progress" manages expectations.

One UX gap: the generated HTML table's "OOBI (SAID)" column truncates the SAID to 12 characters + "…". While this is a space trade-off, users who want to verify a schema must click through to see the full SAID — there is no copy-to-clipboard affordance, no tooltip with the full value, and no `title` attribute on the `<code>` element. This is minor but noted.

### Axis 4 — Accessibility

**Verdict: MEDIUM concern.** The generated `index.html` (in `publish.py:117–139`) has several accessibility gaps:

1. **Missing `lang` attribute on `<html>` element** (WCAG 3.1.1, Level A). The page starts with `<!doctype html>` followed immediately by `<meta charset="utf-8">` — there is no `<html lang="en">` wrapper. Screen readers will guess the language. This is a Level A failure, not an advisory.

2. **Table `<th>` elements lack `scope` attribute** (WCAG 1.3.1). The header row at line 132 has `<th>Schema</th><th>Asserts</th>...` but no `scope="col"`. Without `scope`, some screen readers cannot correctly associate header cells with data cells, especially when the table is rendered in linearized mode.

3. **SAID links use a clipped code string as their text** (`<a href="{s["oobi"]}"><code>{s["said"][:12]}…</code></a>`). The link text is a 12-character cryptographic hash prefix, which is meaningless to a screen reader user. An `aria-label` like `"OOBI for {s['name']}"` would make this navigable by keyboard/screen-reader.

The `index.md` doc pages are Markdown (rendered by Zensical) and their HTML output is not in scope here, but the source docs use `<br>` inside image captions without alt-text on surrounding images (e.g., `faa/index.md`, `face-to-face/index.md`). These images do carry alt text in Markdown `![...]` notation, which is correct.

### Axis 5 — Internationalization

**Verdict: LOW concern for current scope.** The site is English-only by design and carries no explicit locale/localization layer, which is appropriate given that the schemas themselves are technical infrastructure. However:

1. The generated HTML carries no `lang="en"` (overlaps with Axis 4 / WCAG 3.1.1). Any future localization of the registry page cannot start without this attribute set in the source generator.

2. User-visible strings are embedded inline in Python f-strings (`cli.py`, `publish.py`) — there is no message layer or i18n hook. This is acceptable for a developer-tool CLI but would need addressing before any user-facing Zensical page could be localized.

3. The schema `description` fields (which become `<meta description>` tags on the doc site) are well-structured single strings — localizable with a key/translation layer in the future.

## Top findings

### F1: Raw Python traceback on missing repo root — Severity HIGH / Confidence CONFIRMED / `tools/py/src/schematools/repo.py:26`

**Axis:** Error quality (1) and UX (3).

**Evidence:** `find_repo_root()` raises `FileNotFoundError(f"no {REGISTRY_NAME} found at or above {here}")`. The CLI's `main()` in `cli.py:124–126` has no exception handler — so running `schematools check` from outside any schema repo produces a Python traceback. The person who hits this is a first-time contributor or someone running CI outside the expected working directory.

**Who is harmed:** Schema authors, CI operators, and new contributors who run the tool from the wrong directory. The traceback dumps internal module paths and offers no actionable guidance.

**Recommendation:** Add a top-level `try/except` in `main()` that catches `FileNotFoundError` and `KeyError` (and any other predictable failure modes) and replaces the traceback with:

> "I couldn't find a schema repo. I walked up from `{cwd}` looking for `registry.json` and found nothing. Run this command from inside a schema repo, or pass `--root` to point me at one."

---

### F2: `proof-of-control/index.md` — five grammar/spelling errors in two paragraphs — Severity MEDIUM / Confidence CONFIRMED / `proof-of-control/index.md:20,24,36,38,47`

**Axis:** Voice and tone (2).

**Evidence:**
- Line 20: "The parties **follows** a standard challenge…" → "follow"
- Line 24: "This is random number that…" → "This is a random number…"
- Line 36: "issuee's **idetifier**" → "identifier"
- Line 38: "The issuee digitally sign a message…" → "The issuee **should** digitally sign a message…"
- Line 47: "exchange **crypographic** identifiers" → "cryptographic"

**Who is harmed:** Credential verifiers, issuers, and ecosystem integrators reading the primary documentation for the proof-of-control schema. This page appears in the Zensical doc site. Five errors in one page erodes confidence in the technical content.

**Recommendation:** Fix all five in a single editorial pass. No schema change needed; the errors are in the narrative `index.md` only.

---

### F3: HTML landing page missing `<html lang="en">` — Severity MEDIUM / Confidence CONFIRMED / `tools/py/src/schematools/publish.py:117`

**Axis:** Accessibility (4), with i18n overlap (5).

**Evidence:** `_render_index()` emits `<!doctype html>\n<meta charset="utf-8">...` — no `<html>` element, so no `lang` attribute. WCAG 3.1.1 (Language of Page) is a Level A criterion; its absence fails automated accessibility scans and causes screen readers to guess the language.

**Who is harmed:** Blind and low-vision visitors using screen readers, and any future automated a11y audit of the schema.bakobo.com registry page.

**Recommendation:** Wrap the output in `<html lang="en"><head>…</head><body>…</body></html>` and add `scope="col"` to the `<th>` elements. While at it, add `aria-label` or `title` attributes to the truncated SAID links.

---

### F4: `(s)` plural-suffix jargon throughout CLI output — Severity MEDIUM / Confidence CONFIRMED / `tools/py/src/schematools/cli.py:33,72,75,82`

**Axis:** Voice and tone (2).

**Evidence:**
- `"FAIL: {count} problem(s) across {schemas} schema(s) in {root}"` (line 33)
- `"refusing to publish: {len(problems)} problem(s) — fail closed"` (line 72)
- `"published {len(...)} schema(s) to {args.out}"` (line 75)
- `"generated docs for {len(names)} schema(s) in {args.out}"` (line 82)

The `(s)` suffix is a documentation shorthand, not idiomatic English. The brand voice requires natural-language sentences. Every person who runs the tool sees this on every invocation.

**Recommendation:** Use a proper pluralization helper. Python: `f"{n} {'problem' if n == 1 else 'problems'}"` or a one-liner `pluralize(n, 'problem')`. The check summary line should read naturally: `"OK: no problems found across 12 schemas in /path"` or `"FAIL: 3 problems across 12 schemas in /path"`.

### F5: Scattered typos in deployed schema documentation — Severity LOW / Confidence CONFIRMED / multiple locations

**Axis:** Voice and tone (2).

**Evidence (distinct files):**
- `gcd/index.md:7`: "signif**c**antly" → "significantly"
- `faa/index.md:31`: "art**f**act" → "artifact"
- `ai-coder/index.md:17` and `award/index.md:19`: "employee**=**of-the-month" → "employee-of-the-month"
- `gcd/gcd.schema.json:5`: "first-**classes** duties" → "first-class duties" (also: opening verb fragment "Define…" should be a complete sentence)
- `attestation/index.md:5`: "data**(cryptographic**…" (missing space), "**json** data" → "JSON data"

**Who is harmed:** Verifiers and issuers reading schema documentation. Typos in the primary credential documentation for GCD (the flagship schema) are particularly visible. The `gcd.schema.json` description also surfaces as the page's `<meta description>` on the doc site.

**Recommendation:** Single editorial commit fixing all of the above. Note that changing `gcd/gcd.schema.json:5` will invalidate the SAID and require re-saidifying the schema and updating `registry.json` — coordinate this with the next schema version bump.

## What's done well

1. **Clear stream separation in the CLI.** Errors go to stderr; the summary verdict goes to stdout. CI scripts can `grep` the stdout line without needing to parse the full error stream.
2. **The `Problem` format is consistent.** `[check] where: message` is not a complete sentence, but it is uniform across all eight checks — no mixing of capitalization or punctuation styles.
3. **The `check` command's final verdict line is unambiguous.** `OK: 0 problem(s)…` / `FAIL: N problem(s)…` gives a clear binary signal. Passing schemas emit nothing to stderr; CI only sees noise on real failures.
4. **Error messages include offending values.** `"$id 'X' != recomputed 'Y'"` and `"registry path 'gcd/gcd.schema.json' not found on disk"` give the reader something concrete to act on.
5. **The `index.md` doc files for most schemas are well-written and technically detailed.** GCD, FAA, citation, and face-to-face docs clearly explain the purpose, the schema fields, and the governance rules. The GCD doc in particular is thorough and pedagogically useful.
6. **Images in Markdown docs carry alt text.** The `![suggested visual](file.png)` pattern is used consistently, so when these pages render as HTML, the images will have meaningful alt attributes.
7. **The `publish`'s `refusing to publish: N problem(s) — fail closed` message** correctly names the reason (linting failure) and the policy (fail closed). It is actionable: run `schematools check` to see what failed.

## Residual unknowns

1. **Zensical rendering of `index.md` files.** The actual HTML output of the Zensical build step was not available; accessibility of the rendered doc pages (heading hierarchy, link contrast, focus visibility) could not be fully audited. The source Markdown is clean, but a rendered-output audit is needed once the site is live.
2. **Color contrast of the generated `index.html`.** The CSS in `_render_index()` uses `#ddd` for table borders and `system-ui` with no explicit color declarations. Actual contrast depends on the user's OS color scheme. A rendered audit against WCAG AA is needed.
3. **Whether schema `description` strings in `gcd-1.0.0` branch are user-facing.** The `gcd-1.0.0/gcd-1.0.0.schema.json:160` contains the `excercise` typo, but that schema is an archived version. It is unclear whether it appears in the public site's doc pages.
